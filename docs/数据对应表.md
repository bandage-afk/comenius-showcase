# 数据对应表

> **这份文档的用途**：回答一个问题——**前端界面上能看到、能查看的每一样东西，数据库里有没有对应的表和数据？**
> 写于 2026-10-04。配套阅读：`docs/HANDOFF.md`（项目现状）、`docs/ARCHITECTURE.md`（前端架构）。
>
> **使用方式**：接后端/写转换脚本时，照这张表找字段。左列是前端，右列是数据库。

## 0. 三句话结论

1. **能对应上**。前端能显示的每一类东西，`database/` 里几乎都有对应的表；而且字段名是照着前端 TypeScript 类型建的，**`posts` 和 `users` 两张表与前端类型一字不差**。
2. **有一个必须翻译的地方**：点赞数。前端存文字（`'1.5万'`），数据库原来也存文字。现已改造，见第 4 节。
3. **数据库比前端"多"**：78 张表里约 40 张能对应前端显示，其余是 AI 额外编的演示数据（`generated-demo`）和提取代码常量的技术表。

### ⚠️ 读之前必须知道的两件事

- **`database/` 现在是空库**：78 张表结构完整，但**数据已全部清空**（2026-10-04）。本文档表中的"行数"是清空前的历史值，来自 `coverage.json`。
- **本机备份**：`~/Projects/_comenius-database-backup-20251004.sqlite`（清空前的完整数据，含 3903 行，完整性校验 ok）。需要原始数据从这里取。

## 4. 「点赞数」的数据类型改造 ⭐

### 4.1 问题

前端 `Post.likes` 是**给人看的文字**，有两种写法混在一起：

```
200 条帖子里：87 条是 '1.5万' 这种带"万"的，113 条是 '6810' 这种纯数字
```

这带来三个麻烦：**不能排序**（`'1.5万'` 和 `'6810'` 没法比大小）、**不能做加减**（点赞 +1 之后要重新格式化）、**不能统计**。

而且前端已经在"将就"它了——`src/pages/feed/PostLightbox.tsx:68` 干的是：

```
fmtCount(parseCount(post.likes) + (liked ? 1 : 0))
```

也就是**先把文字解析成数字，算完再加回文字**。这个解析逻辑写在 `src/pages/feed/lightboxData.ts:117-120`。

### 4.2 已做的改造

`posts` 表**新增两列**，原来的 `likes` **保留不动**（前端有 5-6 处直接显示它，删了界面会变样）：

| 列 | 类型 | 作用 | 谁用 |
| --- | --- | --- | --- |
| `likes` | `TEXT` | **原始展示字符串**，如 `'1.5万'` | 前端直接渲染（`cards.tsx`、`ProfilePage`、`SearchPage`…） |
| `likes_count` ⭐ | `INTEGER` | **规范数字**，唯一真值来源 | 排序 / 加减 / 统计 / 后端 |
| `likes_display` | `TEXT` | 展示字符串副本（冗余，便于对照） | 兼容/调试 |

**为什么保留三列而不是只留数字**：`'1.5万'` 是**有损**格式——15000 和 15499 都会被格式化成 `'1.5万'`。想 100% 还原界面，必须留着原始文案。**数字列负责"算"，文字列负责"看"。**

### 4.3 转换规则

**文字 → 数字**（前端的 `parseCount`，与 SQL 完全等价，已逐条实测 200/200 一致）：

```
含"万"  : Math.round(parseFloat(去"万") × 10000)
纯数字  : parseInt(去掉逗号和空格)
```

**数字 → 文字**（前端的 `fmtCount`）：

```
≥10000 : (n / 10000).toFixed(1) 去掉末尾的 .0，再加"万"
<10000 : 直接用数字
```

**实测样例**：

| 原文（`likes`） | 数字（`likes_count`） | 格式回文字（`fmtCount`） | 往返一致 |
| --- | --- | --- | --- |
| `'1.5万'` | `15000` | `'1.5万'` | ✅ |
| `'6.8万'` | `68000` | `'6.8万'` | ✅ |
| `'9.9万'` | `99000` | `'9.9万'` | ✅ |
| `'6810'` | `6810` | `'6810'` | ✅ |
| `'2750'` | `2750` | `'2750'` | ✅ |

**验证记录**：200 条全部往返一致，0 条失败；SQL 转换与前端 `parseCount` 逐条比对，0 条不一致。

### 4.4 自检约束（防止存错）

`posts` 表带一条 `CHECK` 约束：**如果 `likes_count` 和 `likes` 对不上，插入直接被数据库拒绝。**

已实测：写入 `('1.5万', 1500)` 会被拒绝（`CHECK constraint failed`），写入 `('1.5万', 15000)` 通过。

这样以后不管是人还是脚本往里塞数据，**都不可能悄悄塞进一个和文案矛盾的数字**。

### 4.5 还需要注意的两件事

1. **`comments.likes` 本来就是 `INTEGER`**，不需要改造（评论点赞数天然是纯数字）。只有 `posts.likes` 有问题。
2. **`likes_count` 目前是空的**：`database/` 已清空，新增的列没有数据。等重新灌数据时，转换 SQL 见 `database/schema.sqlite.sql` 中 `posts` 表的定义与注释。

## 8. 两个抽屉：数据库和图片文件怎么分

> **核心原则**：**文字数字进数据库，图片文件进文件夹，数据库里只记图片的路径。**
>
> 这不是权宜之计，是全世界网站几十年来的标准做法。

### 8.1 为什么必须分两个抽屉

| 判断依据 | 放哪 |
| --- | --- |
| 它是**"一件东西"**（照片、视频本体） | 📦 **文件夹** |
| 它是**"关于东西的信息"**（"张三的头像是第 42 号照片"） | 📒 **数据库** |

**图片为什么不塞进数据库**（SQLite 技术上支持 `BLOB`，但实践上是错的）：

1. **文件爆炸**：1 万张图 × 200 KB ≈ 2 GB。而这个文件里同时装着用户名、帖子、评论，账本胖了之后**连查用户名都变慢**
2. **备份变灾难**：现在备份 = 复制一个 1 MB 文件（1 秒）；图片在里面就是每次备份 2 GB
3. **图片无法被浏览器缓存**，每次都要穿过后端，后端压力大增

> 唯一适合图片进数据库的场景：**极小（几 KB）+ 极少（几十个）**，比如小图标。用户上传的社区配图不属于此场景。

### 8.2 三类文件必须分清

项目里有三类文件，**性质完全不同**，混放会出事：

| 类型 | 例子 | 进 git？ | 部署时 |
| --- | --- | --- | --- |
| **代码 / 应用自带静态资源** | `src/`、`public/`（120 个 WebP + 12 个 PNG，9.8 MB） | ✅ 要 | 构建时打包上传 |
| **用户数据（文字）** | 数据库文件 `*.sqlite` | ❌ **绝不** | 搬过去，独立保存 |
| **用户数据（文件）** | 用户上传的图片 | ❌ **绝不** | 搬过去，独立保存 |

⚠️ **最常犯的错：把用户上传的图放进 `public/`**。三个后果：

1. `public/` 进 git → 用户的图污染代码仓库，仓库无限膨胀
2. `public/` 是"代码" → 每次部署被新版本**覆盖**，用户的图被冲掉
3. `public/` 在 release 目录里 → **`deploy.sh` 设了 `KEEP=5`**（只留 5 个 release），5 次部署后**整个目录被删除**

### 8.3 路径对照：本地 = 服务器（结构对齐）

**本地（开发机）**：


### 8.4 数据库里存成什么样

| 表.列 | 存的值 | 实际文件 |
| --- | --- | --- |
| `users.avatar` | `/uploads/avatars/g1.webp` | `uploads/avatars/g1.webp` |
| `posts.img` | `/uploads/posts/1024.webp` | `uploads/posts/1024.webp` |

**存相对路径**（以 `/uploads/` 开头）的好处：本地和服务器存的**值完全相同**，代码一行不用改
（本地 `http://localhost:3000/uploads/...`，服务器 `https://www.comenius.cn:8443/uploads/...`）。

### 8.5 现状与缺口

| 抽屉 | 现状 |
| --- | --- |
| 📒 数据库 | ✅ **位置已统一在 `database/`**（2026-10-04）：`comenius-demo.sqlite`（78 表，空，当字段字典）+ `backend-dev.sqlite`（9 表，后端在用）。两者结构仍是两套，**未合并**（决策见第 1 节） |
| 📦 图片 | ⚠️ **还没有上传通道**：`uploads/` 目录已建好（2026-10-04），但**后端没有收图片的接口** |

**后端完全没有任何文件上传能力**（搜遍 `backend/src/`：无 `multer` / 无 `multipart` / 无 `express.static` / 无 `/api/upload`）。

**前端现在的"上传"是假的**：`src/pages/PublishPage.tsx` 用
`URL.createObjectURL(file)`（临时内存地址，**刷新即失效**）和 `readAsDataURL`（base64 长串）。
所以**当前用户传的图一律会丢**——这不是 bug，是功能还没建。

### 8.6 补上上传通道要做的三件事（尚未开始）

1. **后端加收图接口**（`POST /api/upload`）：装 `multer`，把文件写进 `uploads/`，返回路径
2. **决定图片存哪**：本地文件夹（简单免费）或对象存储（更专业）
3. **前端改成真上传**：拿到服务器返回的路径，写进数据库 `img` 列

**好消息**：第 3 步改动很小。数据库 `img` 列**本来就在存字符串**（现在是 Unsplash ID `photo-xxx`，
以后是 `/uploads/xxx.webp`，同一种类型），前端拼网址的函数（`src/components/ui/Avatar.tsx`）
改一行从"拼 Unsplash 网址"变成"直接用路径"，**界面代码一行不用改**。
